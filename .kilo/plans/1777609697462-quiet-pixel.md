# Debug and Stabilize Transcription Pipeline and Redis Connectivity - CRITICAL AUDIT & FIX PLAN

## CRITICAL ISSUES IDENTIFIED - Why the Implementation is "Fucked"

### 🚨 CRITICAL BUG #1: Fastify Body Limit is Too Small (1MB default)
**Location:** `src/server.js` line 34
**Problem:** 
- Fastify's default `bodyLimit: 1048576` (1MB) is set in server.js
- The server config has `bodyLimit: 20971520` (20MB) BUT this is IGNORED by @fastify/multipart
- @fastify/multipart uses its OWN limits: `fileSize: 1048576` (1MB) default
- When uploading audio files > 1MB, Fastify rejects with 413 BEFORE reaching the route handler
- This causes the 60-second timeout - client waits for response that never comes

**Evidence from research:**
- "Note that if you are using @fastify/multipart or others plugin. You should specify the limit in the plugin level, because most of them ignore the server specified one." (GitHub issue #5533)
- "For security reasons, @fastify/multipart sets the limit for parts and fileSize being 1000 and 1048576 respectively."

### 🚨 CRITICAL BUG #2: No Multipart File Size Configuration
**Location:** `src/server.js` lines 48-53
**Problem:**
- Multipart is registered WITHOUT fileSize limit override
- Uses default 1MB limit
- Audio files for transcription are typically 1-20MB
- Files > 1MB are silently truncated or rejected

### 🚨 CRITICAL BUG #3: requestTimeout Too Short for Large Files
**Location:** `src/server.js` line 33
**Problem:**
- `requestTimeout: 120000` (2 minutes) seems reasonable
- BUT: slow uploads + processing time can exceed this
- No separate timeout for multipart processing
- Client sees 60s timeout (browser default) while server is still processing

### 🚨 CRITICAL BUG #4: Redis Connection Flapping Causes Job Loss
**Location:** `src/config/redis.js`
**Problems:**
1. `retryStrategy` returns `null` after 10 attempts - STOPS RETRYING completely
2. No keep-alive on idle connections → firewalls/NATs drop them
3. No connection health monitoring → stale connections used
4. Worker duplicate connection has no special handling
5. When Redis drops, BullMQ jobs get stuck in "active" state

### 🚨 CRITICAL BUG #5: No Internal Timeout in Transcription Pipeline
**Location:** `src/services/routerService.js` transcribe()
**Problem:**
- Adapters use 60s timeout (matches client)
- No wrapper timeout in transcribe()
- If Whisper API hangs, client waits full 60s
- No "fail fast" mechanism

### 🚨 CRITICAL BUG #6: Missing Granular Logging
**Problem:**
- Can't tell where in pipeline the hang occurs
- No "Audio received", "Starting Whisper", "Whisper finished" logs
- Can't distinguish between: upload timeout, Redis timeout, API timeout

### 🚨 CRITICAL BUG #7: Worker No Resilience to Redis Disconnects
**Location:** `src/workers/jobWorker.js`
**Problems:**
- No stalled job handling configured
- No reconnection logic when Redis drops
- Worker crashes or hangs when Redis connection closes
- Jobs stuck forever in "active" state

**File:** `src/server.js`

1. Increase multipart fileSize limit to 20MB (matching bodyLimit)
2. Add proper limits configuration
3. Add requestTimeout increase for large file uploads
4. Add connectionTimeout for slow uploads

  limits: {
    fileSize: 20 * 1024 * 1024, // 20MB - match bodyLimit
