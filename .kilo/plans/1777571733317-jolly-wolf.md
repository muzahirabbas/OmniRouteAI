# Plan: Implement /v1/audio/transcriptions Endpoint

## Overview
Implement the audio transcription endpoint with multipart/form-data parsing, provider routing, logging, and tracking, matching the OpenAI-compatible verbose JSON response format.

**Current state**: No existing adapters support audio transcription. The OpenAI adapter supports chat completions with audio input (GPT-4o) but does NOT support the Whisper transcription endpoint. Therefore, new adapters and router service extensions are required.

## Requirements from t.txt
- Parse multipart/form-data payload with fields: file (binary), model, response_format, timestamp_granularities[], language.
- Return verbose JSON with word-level timestamps: `{ text, duration, words: [{word, start, end}] }`.
- Configure middleware to handle multipart (Fastify multipart plugin).
- Implement endpoint logic to process audio in memory, map model correctly.

## Existing Code Analysis
- `src/routes/audio.js`: Contains placeholder endpoints for speech, transcriptions, translations. All return 501.
- `src/server.js`: Fastify server with CORS, auth, routes. No multipart plugin registered.
- `src/services/loggingService.js`: Provides `logRequest` for request logging.
- `src/services/statsService.js`: Provides `trackRequest` for token usage tracking.
- `src/services/routerService.js`: Routes chat completions to providers based on capabilities (vision, audio). Already includes audio detection and provider filtering. However, it only handles chat completions, not audio transcription.
- `src/config/providers.js`: Provider list includes audio feature for openai, google, vertex, etc. Deepgram and assemblyai not listed. These are speech-to-text providers referenced in routerService but not configured.
- `src/adapters/`: Various adapters for chat completions. No audio transcription adapters. The OpenAI adapter supports multimodal audio input (GPT-4o) via `input_audio` but does not support Whisper transcription endpoint.

## Clarifications
- **OpenAI Adapter**: Currently supports chat completions with audio input (GPT-4o). It does NOT support the `/v1/audio/transcriptions` endpoint (Whisper). A separate adapter or extension is needed.
- **Existing Audio Feature**: Providers with `audio` feature are intended for multimodal chat (audio input), not necessarily transcription. However, they could be used for transcription if they expose a compatible API (e.g., OpenAI's Whisper).
- **Deepgram/AssemblyAI**: Mentioned in routerService as providers that do not support text chat completions, implying they are speech-to-text providers. They need to be added to provider config and adapters created.
- **Multipart Parsing**: Not currently used anywhere in the codebase. Need to add `@fastify/multipart` plugin.


## Implementation Steps

### 1. Add Multipart Middleware
- Install `@fastify/multipart` (add to package.json dependencies).
- Register plugin in `src/server.js` before routes.
- Configure limits (max file size, etc.) matching bodyLimit (20MB).

### 2. Extend Provider Configuration
- Research API documentation for Deepgram and AssemblyAI to confirm endpoints, authentication, and response formats.
- Add Deepgram and AssemblyAI as providers in `src/config/providers.js` with appropriate endpoints and audio feature.
- Determine their API endpoints for speech-to-text:
  - Deepgram: `https://api.deepgram.com/v1/listen` (or newer version)
  - AssemblyAI: `https://api.assemblyai.com/v2/transcript`
- Choose model names (e.g., deepgram-nova, assemblyai-default).
- Set appropriate RPM limits (conservative defaults).
- Ensure they have `features: ['audio']` and `status: 'active'`.
- Add them to the static providers list (they will be seeded into Firestore on first run).
- Consider adding provider-specific configuration (e.g., optional parameters like `punctuate`, `profanity_filter`).

### 3. Create Audio Transcription Adapter Interface
- Extend `BaseAdapter` with a new method `transcribe(fileBuffer, model, options)` returning `{ text, duration, words?, language? }`.
- Provide default implementation that throws `ProviderError` indicating transcription not supported.
- Implement provider-specific adapters:
  - `OpenAIWhisperAdapter` (extends BaseAdapter) for OpenAI Whisper models (endpoint: `https://api.openai.com/v1/audio/transcriptions`). Synchronous.
  - `DeepgramAdapter` for Deepgram API (synchronous). Handle authentication via `Authorization: Token {apiKey}`.
  - `AssemblyAIAdapter` for AssemblyAI API (asynchronous). Requires polling for completion. We'll implement a polling mechanism with timeout (e.g., 30 seconds). If async not desired, we can skip AssemblyAI for now.
- Adapters should handle provider-specific request/response normalization and error mapping.
- For each adapter, implement mapping of optional parameters: `language`, `response_format` (e.g., `verbose_json`), `timestamp_granularities[]` (word-level timestamps). If provider does not support word timestamps, we may need to generate them later.
- **Async handling**: For providers that require polling, we can either:
  1. Implement synchronous wrapper that waits for completion (blocking) – may increase latency.
  2. Return a pending response and require client to poll (not OpenAI-compatible).
  We'll choose option 1 for simplicity, but limit polling time to avoid long waits.

### 4. Update Router Service for Audio Transcription
- Add new task type `audio_transcription` in `routerService.js`.
- Modify `route` function to support audio transcription task type, filtering providers with `audio` feature.
- Add `transcribe` method to routerService that:
  - Calls `route` to select provider/model/key.
  - Retrieves adapter via `getAdapter`.
  - Calls adapter.transcribe with file buffer and options.
  - Handles retries/failover (reuse existing retry logic with MAX_ATTEMPTS).
  - Returns normalized result with provider, model, keyUsed, tokens, etc.
- Ensure token estimation for audio (maybe based on duration). Use `estimateTokens` as fallback.
- Integrate logging and tracking within the transcribe method (or let endpoint handle it). We'll keep logging at endpoint level for consistency with chat endpoints.

### 5. Implement Transcription Endpoint in audio.js
- Replace placeholder with actual handler.
- Use `@fastify/multipart` to parse request.
- Extract fields and validate.
- Determine model and provider (default to openai for whisper-1).
- Call routerService.transcribe with file buffer and options.
- Log request via `logRequest` and track usage via `trackRequest`.
- Map adapter response to verbose JSON format (including word timestamps if available). If provider does not return word timestamps, we may need to generate them using alignment (optional). For MVP, we can omit words array if not provided (but spec expects it). We'll need to decide: either require providers that support word-level timestamps, or generate approximate timestamps based on word count and duration.
- Handle errors and return appropriate OpenAI-style error responses.

### 6. Logging and Tracking Integration
- Ensure `logRequest` is called with provider, model, latency, tokens, status.
- Ensure `trackRequest` is called with token counts (input tokens estimated from audio duration).
- Use existing Redis/Firestore pipelines.

### 7. Error Handling
- Map provider errors to HTTP status codes (400, 401, 429, 500).
- Return OpenAI-compatible error objects.

### 8. Testing
- Write simple curl commands to test endpoint with sample audio file (WAV format).
- Verify response format matches OpenAI spec (including word timestamps if available).
- Ensure logging entries appear in Firestore.
- Test each provider (OpenAI, Deepgram, AssemblyAI) separately to confirm adapter functionality.
- Test error scenarios: invalid API key, unsupported file format, large file size, missing required fields.
- Measure latency and ensure it's within acceptable limits (especially for async providers).

## Risks
- Missing audio transcription adapters for providers other than OpenAI.
- Token estimation for audio may be inaccurate.
- Multipart parsing may conflict with existing body parsing.
- Word-level timestamp generation may be complex.
- Async providers (AssemblyAI) require polling, increasing latency and complexity.
- Provider API changes or authentication differences may cause integration issues.

## Mitigations
- Start with OpenAI Whisper only; add other providers later.
- Use conservative token estimation (e.g., 1 token per 0.1 second).
- Ensure multipart is only enabled for audio endpoints.
- For word timestamps, if provider does not supply, we can omit words array (but spec expects it). We'll need to decide: maybe we can return empty array or approximate using word count and duration. We'll implement a simple alignment using word count and equal distribution.
- For async providers, implement polling with timeout (max 30 seconds) and fallback to synchronous error if timeout exceeded.
- Write unit tests for each adapter to ensure compatibility.

## Open Questions
1. **Word-level timestamps**: Should we require providers to return word timestamps? If not available, should we generate approximate timestamps (e.g., equal distribution of duration across words) or omit the `words` array (breaking OpenAI spec)? The spec expects `words` array; we could default to empty array but that may cause client errors.
2. **Provider priority**: Which providers should be supported initially? OpenAI Whisper is a safe start. Should we also add Deepgram and AssemblyAI now, or later?
3. **Multipart plugin**: Is `@fastify/multipart` already installed as a transitive dependency? If not, we need to add it to package.json (requires npm install). Can we proceed with adding it?
4. **Token counting**: How should we estimate input tokens for audio? OpenAI's Whisper uses a token per ~0.1 second? We'll need a formula.
